Инженерный дневник

Я собираю браузерную мастерскую без обязательного облака

Как устроен статический каталог инструментов, какие задачи можно выполнять на устройстве пользователя и почему локальную обработку нужно проверять, а не просто обещать.

Главная идея: для ряда операций браузеру не нужен отдельный сервер. Если вычисление выполняется JavaScript-кодом на устройстве и исходные данные не уходят во внешний сервис, пользователь может обработать текст или файл прямо в открытой вкладке. Это не универсальное обещание для всего сайта: каждую функцию нужно проверять отдельно.

Зачем собирать инструменты в одном месте?

Я хотел объединить небольшие повседневные инструменты, функции для разработчиков, работу с текстом и данными, обработку файлов и эксперименты. Вместо десятков разрозненных закладок получается каталог, где можно найти нужную операцию и посмотреть, как она устроена.

В мастерской есть браузерные инструменты, рабочая область, локальная мастерская и справочник альтернатив. Отдельно живёт лаборатория шуточных калькуляторов — серьёзный вклад в абсолютно несерьёзную математику.

Что означает локальная обработка?

Локальная обработка означает, что конкретная операция выполняется средствами браузера на устройстве пользователя. Например, форматирование текста или преобразование данных может выполняться клиентским JavaScript без передачи исходного содержимого на сервер.

Но загрузка страницы, библиотек, шрифтов или моделей может требовать интернет. Инструмент может обращаться к API, WebRTC-узлу или другому внешнему сервису. Поэтому точнее говорить «эта операция выполняется локально», чем объявлять весь сайт полностью офлайн.

Как проверить сетевые зависимости?

  1. Откройте инструмент в отдельной вкладке и вызовите инструменты разработчика (DevTools).
  2. Перейдите во вкладку Network и включите сохранение журнала запросов.
  3. Очистите список, выберите тестовый файл без личных данных и выполните одну операцию.
  4. Проверьте Fetch/XHR, WebSocket и другие обращения: адрес, метод, размер отправленных данных и payload.
  5. Повторите тест без сети, если функция обещает офлайн-работу, и проверьте, что результат действительно формируется.

Одна проверка не доказывает безопасность всего сайта. Повторяйте её после обновлений и проверяйте сторонние зависимости.

Почему выбран статический хостинг?

GitHub Pages публикует статические файлы: HTML, CSS, JavaScript и ресурсы. Это удобно для страниц, где вычисления происходят в браузере, и не требует собственного постоянно работающего бэкенда. Обратная сторона — на GitHub Pages нельзя запустить произвольный серверный процесс; функции, которым нужен бэкенд, требуют отдельной инфраструктуры или внешнего провайдера.

Что ещё входит в мастерскую?

Помимо веб-утилит, у меня есть Android-приложения, программы для Windows и Linux, игры и экспериментальные проекты. Для заметных приложений создан отдельный каталог с описанием требований, ограничений и исходников.

Что предстоит улучшить?

План — проверять утилиты в разных браузерах, улучшать мобильный интерфейс, ускорять загрузку, описывать сетевые зависимости и расширять автоматические тесты. Важнее честно указать ограничение конкретной функции, чем написать «100% приватно» и спрятать за ним сетевой запрос.

Частые вопросы

Означает ли браузерная обработка, что весь сайт работает офлайн?

Нет. Отдельные инструменты могут требовать загрузку библиотек, моделей, внешних API или сетевого обмена. Проверяйте конкретный сценарий.

Как проверить, отправляет ли инструмент файл на сервер?

Откройте DevTools → Network, очистите список запросов, выполните одну операцию и проверьте, отправлялись ли содержимое файла, текст или другие пользовательские данные.

Почему выбран GitHub Pages?

Для статических страниц и клиентских операций не обязательно поднимать собственный постоянно работающий сервер. Серверные функции при этом остаются за пределами обычного GitHub Pages.
